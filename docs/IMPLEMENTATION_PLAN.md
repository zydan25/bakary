## 1. ملخص العمل

إنشاء نظام أعمال متكامل للمخبز بواجهة عربية RTL، موجهة للهاتف أولًا، باستخدام Python وFlask وPostgreSQL. يفصل النظام بين واجهات المستخدم، ومسارات HTTP، وقواعد العمل، ونماذج قاعدة البيانات، ويعتمد Blueprints ومهاجرات قاعدة البيانات بدل تجميع النظام في ملف واحد.

### أهداف المشروع

- إدارة الموزعين والعملاء وتسعير كل صنف وتسجيل عمليات الصرف والتحصيل وكشوف الحساب.
- إدارة المنتجات المخبوزة والمواد الخام والمخزون الافتتاحي والإضافات والاستهلاك.
- تسجيل العجنات والإنتاج، ثم إقفال الفترة وتسجيل التوزيع المجاني والتالف والمتبقي وتسليمات المستلم.
- إدارة الصندوق والمصروفات والحسابات النقدية وحركة الأموال.
- إدارة الموظفين والمستخدمين والأدوار والصلاحيات، مع واجهة ملائمة لكل دور.
- توفير تقارير يومية وتقارير فترة وكشوف حساب قابلة للطباعة وحفظ إيصال العملية كصورة.
- تقديم تجربة PWA قابلة للتثبيت، مع تحديثات واضحة وتعامل آمن مع انقطاع الشبكة.

## 2. نتيجة فحص البداية والمرجع البصري

- تم التحقق من أن مستودع `bakary` كان فارغًا قبل بدء العمل.
- تمت مراجعة `README.md` و`templates/base.html` و`templates/dashboard.html` و`static/css/style.css` في مستودع `water-pos-postgres`.
- تم اعتماد الاتجاه البصري الظاهر في الصورة المرفقة: خلفية فاتحة قريبة من `#f6f8fb`، لون أزرق رئيسي `#1a56db`، بطاقات بيضاء بحواف هادئة، حدود خفيفة، وأيقونات واضحة. ستُعاد صياغة المحتويات والأيقونات لتناسب المخبز بدل نسخ الوظائف الخاصة بنظام المياه.
- تم اعتماد خط عربي واضح (Tajawal أو بديل محلي مناسب)، وRTL كامل، وتصميم حقيقي يبدأ من عرض 360px، مع اختبار 360×800 و390×844 و412×915.
- تم اعتماد قائمة ERP شجرية للأقسام على سطح المكتب تتحول إلى Drawer على الهاتف، مع Bottom Navigation للأقسام الأكثر استخدامًا. تُحفظ الأقسام المفتوحة في `localStorage` ويُفتح القسم الحاوي للمسار الحالي تلقائيًا.

## 3. قرارات البنية التقنية

### الخادم وقاعدة البيانات

- Python 3.10+.
- Flask باستخدام Application Factory في `app/__init__.py`.
- تقسيم الميزات إلى Flask Blueprints، وتجنب حشر المسارات والمنطق في ملف `app.py` واحد.
- Flask-SQLAlchemy وSQLAlchemy ORM، مع كائن مشترك واحد `db` وجلسة موحدة يديرها Flask-SQLAlchemy؛ تنتهي الجلسات/المعاملات بطريقة سليمة في نهاية الطلب.
- Flask-Migrate/Alembic لجميع تغييرات مخطط القاعدة، ودعم `flask db upgrade` في النشر.
- PostgreSQL: قاعدة `bakary`، المستخدم `bakary`، كلمة مرور التطوير المطلوبة `bakary` على البيئة المحلية. تكون بيانات الاتصال في `.env` غير المرفوع إلى Git، ويُوثق إعداد الإنتاج منفصلًا.
- استخدام `Decimal` وحقول `NUMERIC` للمبالغ والأسعار، لا `float`.
- خدمات مستقلة لقواعد العمل والمعاملات المالية، والتحقق من المدخلات على الخادم، ومعالجة أخطاء موحدة، وسجلات تدقيق للأحداث الحساسة.
- عدم حذف العمليات المالية المسجلة عند حذف كيان؛ يُستخدم التعطيل/الأرشفة، وتُحفظ قيمة السعر والوصف وقت حدوث العملية للحفاظ على صحة التاريخ.

### الواجهة وتجربة الاستخدام

- Flask/Jinja2 وBootstrap RTL، مع CSS وJavaScript منظمين ومكونات قابلة لإعادة الاستخدام.
- تصميم Mobile-First؛ بلا نماذج مفتوحة تلقائيًا. تظهر النماذج في نافذة منبثقة/Drawer عند الضغط على زر إضافة أو إجراء.
- حقول الاختيار المخصصة: قائمة بيضاء أسفل الحقل، نص أسود، بحث فوري أعلى القائمة، تمرير داخلي، حالة مختارة ظاهرة داخل الحقل، ودعم لوحة المفاتيح وإمكانية الوصول.
- كل حقل مبلغ يُظهر المبلغ كتابةً بالعربية أسفله فور الكتابة، باللون الأحمر وبخط ثقيل، مع التحقق النهائي من القيمة على الخادم.
- نموذج الصرف يبقى مفتوحًا بعد النجاح، ويمنع الإرسال المكرر، ثم يصفر الحقول عدا الصنف الافتراضي المحدد.
- حالات Loading وEmpty وError وDisabled وPressed/Focus، ورسائل نجاح وفشل صريحة.
- لا تستخدم جداول عريضة على الهاتف؛ تعرض البيانات كصفوف/بطاقات مرنة، وتُستخدم الجداول الثنائية المدمجة فقط حيث تكون مفيدة، مثل التسعير.
- PWA بملف manifest وأيقونات مناسبة وService Worker وتحديثات واضحة وصفحة عمل عند انقطاع الاتصال. تُعامل الكتابات المالية والإقفال بحذر: لا تُعرض العملية كمسجلة نهائيًا حتى يؤكدها الخادم. أي طابور حفظ دون اتصال يستخدم معرّفًا فريدًا لمنع تكرار العملية عند المزامنة، ويعرض العمليات المعلقة بوضوح.

## 5. معايير الجودة المشتركة لكل مرحلة

1. لا تُغيّر قاعدة البيانات خارج migration موثق.
2. لا تكون صلاحية الوصول مجرد إخفاء زر؛ تحقق الصلاحية في الخادم والخدمة.
3. تُنفذ الحركة المالية أو حركات المخزون ذات الصلة داخل transaction ذرية.
4. لكل عملية مهمة: منشئها، وقتها، تاريخ العمل، مرجعها، حالتها، وسبب التعديل/الإلغاء.
5. لا تتغير النتائج التاريخية عند تعديل قائمة الأسعار.
6. لا يمكن مضاعفة الحركة عند النقر المتكرر أو إعادة الطلب بعد انقطاع الشبكة.
7. لا يظهر نجاح للعميل قبل تأكيد الحفظ الفعلي.
8. لا تظهر واجهة إضافة أو تعديل مفتوحة تلقائيًا؛ تبدأ من زر واضح.
9. لا تنشأ بيانات تجريبية في الإنتاج تلقائيًا، عدا أمر إعداد أول مدير موثق وآمن.
10. بعد كل مرحلة: فحص الملفات المعدلة، وتشغيل الاختبارات المتاحة، وتوثيق الناجح والفاشل والمتبقي.

## 6. الأوامر المستهدفة على الخادم (بعد تجهيز المرحلة الأولى)

هذه أوامر التشغيل المستهدفة. ملفات المشروع وأوامر الإعداد أضيفت، لكن يجب تنفيذها والتحقق من نتائج PostgreSQL والاختبارات قبل اعتماد النشر:

```bash
cd /home/root/projects/bakary
git pull --ff-only origin main
source .venv/bin/activate
pip install -r requirements.txt
flask --app wsgi:app db upgrade
flask --app wsgi:app seed-roles
flask --app wsgi:app seed-defaults
pytest
pm2 restart bakary --update-env
pm2 save
```

على إعداد النشر، يعمل Gunicorn خلف PM2 على `127.0.0.1:4043`، وتُجهز قيمة `DATABASE_URL` في البيئة المناسبة. إذا لم تكن عملية PM2 قد أنشئت بعد، تُستخدم خطوة التشغيل الأولى الموثقة في ملفات المشروع بدل `restart`.

## 7. ملاحظات تحتاج حسمًا أثناء المرحلة المناسبة

- مزود إرسال رمز استعادة كلمة المرور؛ سيُبنى التدفق دون تثبيت مزود غير محدد.
- وحدات قياس المواد الخام وطريقة التحويل إن استُخدمت وحدات مختلفة.
- هل تُسمح أرصدة سالبة أو إلغاء حركة مالية بعد ترحيلها؟ الافتراضي المقترح: لا رصيد مخزون سالب ولا حذف لحركة مالية مرحلة؛ التصحيح بحركة عكسية بصلاحية خاصة.
- طريقة تحميل تكلفة المواد الخام وربحية المنتج ليست مفترضة في المرحلة الأولى؛ يركز النظام أولًا على الكميات والأسعار والأرصدة التي حددها المستخدم.
- أي إدخال دون اتصال لا يعد قيدًا ماليًا نهائيًا قبل المصادقة والمزامنة على الخادم.
